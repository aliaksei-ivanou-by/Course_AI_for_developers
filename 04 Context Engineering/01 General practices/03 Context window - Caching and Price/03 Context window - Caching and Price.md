# Context Windows, Prompt Caching, Cost, and Performance

Context engineering affects more than whether a request fits within a model's limit. It also affects repeated input processing, latency, cost, and the model's ability to focus on current evidence.

The objective is not to make every prompt or context as small as possible. It is to provide the smallest **sufficient and relevant** context for completing the task correctly. Removing necessary information can increase total cost by forcing the agent to rediscover the project, make avoidable mistakes, or require additional turns.

> **Version and billing note:** Token categories, cache lifetimes, context limits, model prices, and subscription allowances change. A cost shown by Claude Code may be an API list-price estimate rather than an additional charge to a subscription account. Verify the active authentication method, provider, model, and current pricing before treating an on-screen value as an invoice.

## Context Is the Model's Working Set

For a model request, the context can include:

- System and developer instructions
- Repository instructions such as `CLAUDE.md` or `AGENTS.md`
- The current user message
- Relevant earlier messages and assistant responses
- Tool definitions
- Tool calls and their results
- Files, logs, images, and documents loaded for the task
- Generated reasoning and the space reserved for the response

In a conventional multi-turn API conversation, earlier turns are included again in later requests. Agent products can also compact, summarize, prune, or otherwise manage that history.

The context window is the maximum working set for one request. It is not the same as cumulative session usage or account usage.

```text
context window       capacity of one model request
current context      material available in this request
session usage        tokens accumulated across many requests
account usage        usage aggregated across sessions and users
billable cost        price after model, cache, plan, and provider rules
```

## What Prompt Caching Actually Does

Agent requests often share a large stable prefix: system instructions, tool definitions, project guidance, files, and earlier conversation history. Prompt caching allows the provider to reuse computation for an identical or compatible prefix instead of processing that prefix from scratch at the standard input rate.

Caching changes the economics and often the latency of repeated input. It does **not** remove that input from the model's context.

```text
stable request prefix
        ↓
first eligible request ── cache creation/write
        ↓
later matching request ── cache read/hit
        ↓
model still considers the cached tokens as context
```

This distinction is essential:

- Cache storage is not long-term semantic memory.
- A cache hit does not mean the model ignores the cached text.
- Cached tokens still count toward context-window capacity.
- Caching does not repair irrelevant or contradictory context.
- Compaction reduces the active context; caching normally does not.

## Reading the Usage Categories

Claude API usage reports commonly separate input into three categories.

| Usage field | Meaning |
| --- | --- |
| `input_tokens` | Input not read from or written to the prompt cache, normally the portion after the last cache breakpoint |
| `cache_creation_input_tokens` | Tokens used to create a new cache entry; interfaces may label this **cache write** |
| `cache_read_input_tokens` | Tokens retrieved from an existing cache entry; interfaces may label this **cache read** |
| `output_tokens` | Tokens generated by the model |

For an individual API response, total input is conceptually:

```text
total input tokens
    = uncached input
    + cache creation input
    + cache read input
```

A Claude Code usage screen may aggregate these categories across many turns. Therefore, values such as `100,000 cache read` and `200,000 cache write` cannot by themselves reveal the current context size or the cost of the next request.

### Cache Write

A cache write means that an eligible prompt prefix is being stored for possible reuse. The write can include instructions, tool definitions, documents, or conversation content depending on where the cache boundary is placed.

Creating a cache entry is generally priced differently from ordinary input and can carry a premium. It is an investment that becomes useful only if later requests reuse the entry before it expires.

### Cache Read

A cache read means that a later request matched a cached prefix. It is normally priced below standard uncached input and can reduce time to the first output token.

The model still receives the logical content represented by those tokens. They continue to occupy context capacity and can still distract the model if they are irrelevant.

### Cache Misses and Rewrites

A cache may not be reused when:

- The stable prefix changes
- Content is reordered
- Tool definitions or tool configuration change
- The entry expires
- The prompt is shorter than the provider's minimum cacheable length
- A different model or incompatible platform configuration is used

High cache-write volume is not automatically a defect: the first request must populate a cache, and a growing agent conversation may write new suffixes. Investigate repeated writes when a supposedly stable workload produces few reads.

## Why a Dollar Amount Is Not Self-Explanatory

The cost of one request can include several categories:

```text
request cost
  ≈ uncached input × input rate
  + cache writes × write rate for their lifetime
  + cache reads × read rate
  + output × output rate
  + separately priced tools or infrastructure
```

The exact rates depend on the selected model, cache duration, provider, and any long-context or regional pricing rules. A session estimate also depends on whether the displayed counts are per-request or cumulative.

Authentication changes how the number should be interpreted:

| Access mode | Typical interpretation |
| --- | --- |
| Anthropic API key | Token usage is generally billed according to API rates |
| Claude Pro or Max account | Usage is governed by subscription allowances; a displayed list-cost estimate may not be a separate charge |
| Enterprise account or LLM gateway | Organization-specific contracts, routing, budgets, or reporting may apply |
| Amazon Bedrock, Google Vertex AI, or another provider | Provider pricing and usage-field behavior can differ |

Use the provider's usage and billing report for financial reconciliation. A local session figure is useful for comparing workflows, but it should not be treated as the authoritative invoice without confirming its definition.

## Why Long Context Can Hurt Performance

More context is not automatically better. A long session can accumulate obsolete plans, duplicate files, failed approaches, large tool outputs, and requirements from a different objective.

This can have several effects:

- **Higher input cost:** More material is processed or retrieved on later turns.
- **Higher latency:** Large uncached inputs take longer to process; caching may reduce but not eliminate this effect.
- **Reduced effective attention:** Relevant facts compete with stale or unrelated content.
- **Greater contradiction risk:** An old decision may conflict with a newer requirement.
- **Earlier compaction:** The agent reaches its context threshold sooner and must summarize or discard detail.
- **Larger operational footprint:** Tool schemas, logs, images, and generated output all consume capacity.

However, reducing context too aggressively can also hurt:

- The agent may repeat repository exploration.
- Missing constraints may cause incorrect changes.
- A summary may omit a critical edge case.
- More clarification and repair turns may outweigh the tokens saved.

Optimize the completed task, not the length of a single prompt.

## Caching and Context Reduction Solve Different Problems

| Technique | Reduces active context? | Can reduce repeated-input cost? | Primary purpose |
| --- | ---: | ---: | --- |
| Prompt caching | No | Yes | Reuse computation for a stable prefix |
| Focused file and log selection | Yes | Yes | Avoid loading irrelevant evidence |
| Compaction | Yes | Usually | Replace older detail with a task-preserving summary |
| New session | Yes | Yes | Isolate a new objective from old conversation state |
| Persistent project files | Indirectly | Yes | Reload concise, durable state instead of chat history |
| Disabling unrelated tools or MCP servers | Yes | Yes | Remove unused tool definitions and instructions |

An effective workflow often uses several techniques together. Prompt caching makes repeated relevant context cheaper; pruning and compaction keep irrelevant context out.

## Practical Context Hygiene

### Start a New Session When the Objective Changes

Do not carry an unrelated feature, investigation, or review into the same conversation merely because context space remains. Save accepted state in the repository, then begin a focused session for the new objective.

### Compact a Continuing Task

Use the agent's compaction command when the objective remains the same but the conversation has accumulated substantial exploration. Verify that the summary preserves requirements, decisions, unresolved questions, modified files, and validation results.

### Load Only the Evidence Needed

Do not delete legitimate project files merely to save tokens. Instead:

- Read the relevant section rather than the entire large file.
- Filter logs to the failing time range or error signature.
- Search for symbols before opening neighboring code.
- Avoid attaching duplicate documents.
- Remove accidental or irrelevant attachments from the request.

### Keep Durable State Outside the Conversation

Store requirements, plans, decisions, progress, and verified commands in versioned project artifacts. A fresh session can recover from those files more reliably than from a vague recollection of an extremely long chat.

### Keep Stable Prefixes Stable

For direct API integrations, put stable reusable material before frequently changing content and avoid needless changes to tool definitions or cached instructions. Measure cache reads and writes rather than assuming the cache is effective.

In a managed coding-agent product, the harness may control cache boundaries automatically. Do not restructure repository instructions solely to manipulate caching unless measurements show a real benefit.

### Limit Tool Noise

Large tool catalogs and verbose results consume context. Enable only integrations relevant to the project, request bounded output, and return concise findings from isolated research.

### Choose Model and Reasoning Effort Deliberately

Context hygiene is only one cost lever. A capable but expensive model may be appropriate for architecture or a difficult defect, while routine transformations may use a faster model. Excessive reasoning effort can also increase output-side usage. Measure quality and rework, not just the nominal price per token.

## A Better Cost-Review Workflow

1. Confirm the model, provider, authentication method, and billing mode.
2. Inspect current context occupancy separately from cumulative session usage.
3. Break input into uncached, cache-write, and cache-read categories.
4. Include output tokens and separately charged tools.
5. Check whether the values are per-request, per-session, or account-wide.
6. Compare completed tasks of similar difficulty, not isolated prompts.
7. Investigate low cache reuse, unexpectedly large tool results, and repeated discovery.
8. Change one lever at a time and verify that quality and completion time do not regress.

Useful questions include:

```text
Did the agent load evidence unrelated to the task?
Did it repeatedly rediscover facts that belong in project instructions?
Did stable prefixes produce cache reads?
Did compaction preserve the decisions required to finish?
Did a shorter context create extra correction turns?
Was the displayed cost an API charge or only a list-price estimate?
```

## Common Mistakes

- Assuming cached tokens no longer occupy the context window
- Treating cache read as persistent memory
- Adding cache reads, cache writes, and uncached input without checking whether the interface already reports a total
- Inferring the next request's size from cumulative session counters
- Treating a local dollar estimate as an invoice for every authentication mode
- Hard-coding prices from a video into budgets or documentation
- Deleting project files instead of controlling what the agent loads
- Compacting without preserving critical requirements and progress
- Starting a new session without leaving durable handoff state
- Minimizing token count so aggressively that the agent must repeat work
- Assuming lower token usage always means a faster or higher-quality completed task

## Key Takeaway

Prompt caching and context management are complementary. Cache writes store an eligible stable prefix, and cache reads reuse it at a discounted processing rate; both still count as context available to the model. Keep the active context focused to reduce waste and distraction, but preserve everything necessary to complete the task correctly. Evaluate cost using the full usage breakdown and the actual billing mode, then optimize end-to-end task quality, latency, and spend together.
